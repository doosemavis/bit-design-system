## Problem Statement

bit is an open-source React design system with retro-game themes, built for people new to design systems. Its one rule: the prop you type is the class it emits, which is the token it reads. Today bit has **no hosted docs**. The README tells visitors to clone the repo and run Storybook locally. The package can't be installed: `@bit/react` is `"private": true` at `0.0.0`, and the `@bit` npm scope belongs to another organization. Code copied from Storybook leaves out the two CSS imports, which appear only in the README's install section, so it renders unstyled when pasted. The README's own snippet also puts those imports in the wrong order for its fonts note. A newcomer never sees bit working as a whole app.

## What Makes This Cool

- The docs site is built entirely from bit, with no hand-rolled versions of anything bit provides. Visitors explore bit by using bit, and newcomers get a full app to read and copy from.
- Every component page is a live playground. Change a control and the preview, the React code and the HTML code all update together, and the URL updates too, so any state is shareable. Copy gives you a file that works on paste.
- Retro touches stay crafted rather than loud. The 8 → 16 → 32 → 64 logo grows from its right edge and stays centered on the hyphen. Code blocks use the "Ink night" scheme, where every token color is at least 5.6:1 against `#151515`.

## Constraints

- Open source and a learning project for the owner (builder mode). A solo owner, so review load has to stay humane.
- **Computer-only:**
  - The gallery has one desktop layout with `min-width: 1024px`. Narrower windows scroll horizontally, and nothing reflows.
  - The sidebar collapse below 720px that's already built (Task 2) is **removed** in T8, along with its menu toggle and test.
  - Playwright and axe run at 1280×800. Phone and tablet layouts are in TODOS.md.
  - T11 amends addendum §C.2.4, which says "responsive," to say "desktop-only, min-width 1024px; mobile deferred (TODOS.md)."
- No docs framework, UI kit or highlighter library. The gallery uses `@bit-ds/react` only through its public `exports` map.
- One theme (power-up). Size tokens are px-named (space, radius, type). Their logged limit: the names are only accurate for power-up's scale.
- **Canonical CSS import order is theme first:** `import '@bit-ds/react/themes/power-up.css';` then `import '@bit-ds/react/styles.css';`. The theme's Google Fonts `@import`, which now includes JetBrains Mono, must stay first when bundlers concatenate CSS. Home, the full file and the README all use this order.

## Premises (agreed 2026-10-02)

1. The gallery is bit's only docs surface and its first real app. Built from bit, it doubles as the reference app newcomers can read.
2. Ship it as a stack of reviewable PRs (foundation, then components, then gallery), not one giant PR.
3. The docs must not promise an install that fails. The first 0.x npm publish (in the `@bit-ds` org) ships with the gallery, and the live docs never point at an unpublished version.
4. Px-named tokens stay, with the logged ceiling: correct for power-up, revisit when a second theme needs a different scale.

## Approaches Considered

### Approach A: Stacked PRs, library first (chosen)
Detail below.
### Approach B: Gallery first, upgrade after
Ruled out. Visitors would touch non-bit stand-ins at launch, contradicting dogfooding, and the stand-ins would be built only to be deleted.
### Approach C: Vertical slices, one PR per component
The runner-up for visible momentum. Ruled out because it means about 12 PRs, about 4× the CI and review overhead, and a forced forms-first order.

**Library vs gallery:**
- Public in `@bit-ds/react`: `Code` (inline) and `CodeBlock` (highlighting through an internal, unexported tokenizer for jsx, html, css and shell; a copy button with the copy-failure state).
  - Rationale: apps built with bit for developers display code. Lemon UI ships CodeSnippet for the same reason.
- Gallery-private: `toJsx`, `toHtml`, the full-file wrapper and the manifest engine.

**Dogfooding checks (T9, PR3 gate):**
- ESLint `no-restricted-syntax` bans raw `<button>`, `<a>`, `<input>`, `<select>`, `<textarea>`, `<table>`, `<code>` and `<pre>` JSX in `apps/gallery/src`. This forces the ControlsPanel's raw controls and any leftover raw markup onto bit components. ThemeSelect is hidden while there's one theme, but it's rewritten on bit Field and Select anyway.
- A test parses `gallery.css` and fails if any `gallery-*` rule sets a property outside a layout-only set: `display`, `grid*`, `flex*`, `gap`, `align-*`, `justify-*`, `place-*`, `width`, `min-width`, `max-width`, `height`, `min-height`, `margin*`, `padding*`, `position`, `inset`, `top`, `right`, `bottom`, `left`, `overflow*`, `z-index`.

**Version display (T9):** Home's install step shows a Badge `v{version}`. The version is read from `packages/react/package.json` at build time through Vite `define`, with a test.

**Snippet strings (T12):**
- `apps/gallery/src/content/snippets.mjs` is plain ESM, imported by both the gallery and the smoke script. It exports:
  - `INSTALL_COMMAND` (`pnpm add @bit-ds/react`)
  - `STYLE_IMPORTS` (theme first)
  - `fullFile(jsx)`, which wraps JSX in the standalone example: the two style imports with the comment `// once per app: skip if already in your entry file`, the component import, and an `Example` component
- The gallery's React tab calls `fullFile(toJsx(...))`.

**Consumer smoke (T12, extends `scripts/smoke-consumer.mjs`):**
1. `npm pack` `@bit-ds/react`.
2. Assert the package name in `INSTALL_COMMAND` equals `packages/react/package.json` `name`, then install the tarball path in its place.
3. Scaffold a minimal Vite React app whose `main.jsx` is exactly `STYLE_IMPORTS` plus `fullFile('<Button>Save</Button>')`, and run `vite build`.
4. Assert the built CSS's first rule is the Google Fonts `@import`.
5. Serve the build with `vite preview`. Playwright Chromium asserts the button has class `bit-button bit-primary` and computed `background-color: rgb(124, 58, 237)` (`#7C3AED`).

**Release (T11 owns the workflow, replacing the original push-to-main `deploy.yml`):**
> **Superseded (2026-10-04):** PR3c ships one `release.yml` (guard, publish, deploy) beside `ci.yml`, not three workflow files. See `docs/superpowers/specs/2026-10-04-pr3c-release-design.md`.

- **`release-dry-run`** (on `pull_request`): build, `npm pack`, `npm publish --dry-run`, the consumer smoke, and a gallery build. This is PR3's gate.
- **`release`** (on tag `v*`), with three jobs:
  1. **guard:** fail unless the tag equals `v` + `packages/react/package.json` version and the tagged commit is on `main`.
  2. **publish:** skip if `npm view @bit-ds/react@<version>` already exists, which makes re-runs safe; otherwise `npm publish --provenance --access public` (`id-token: write`). Then install `@bit-ds/react@<version>` from the registry in a scratch app as a post-publish check.
  3. **deploy:** needs publish; builds and deploys the gallery to Pages. It can be re-run alone if Pages fails.
- **`docs-deploy`** (`workflow_dispatch`): a docs-only fix path. It rebuilds and deploys the gallery only if the version the gallery shows already exists on npm, so premise 3 holds without cutting a release for a typo.
  - **Superseded (2026-10-04):** `docs-deploy` is not built. A docs fix ships as a patch release through the tag workflow. See the 3c spec, `docs/superpowers/specs/2026-10-04-pr3c-release-design.md`, and the TODO in `TODOS.md`.
- **npm auth:** the first publish uses a granular npm token stored as repo secret `NPM_TOKEN`, created by the owner. After the package exists, switch to npm trusted publishing (configured on npmjs.com for this repo and workflow) and delete the secret.

## What I noticed about how you think

- On the code samples you said, "I want the code snippets to display the code in the multi color examples of other code editors, not just the bland one color." You judged the docs by how they feel to read, not only by what they contain.

### R3-3 — consistency

**Problem**

The gallery's own entry, `apps/gallery/src/main.tsx`, imports `styles.css` before `themes/power-up.css`, and nothing changes that. ### R3-4 — feasibility

**Problem**

> The gallery.css test allows only layout properties in `gallery-*` rules: no background, border, border-radius, box-shadow, color or font. Several approved designs need exactly those, and no bit component provides them: the Playground's checkerboard stage behind its Switch, the Tokens page's color cards, its space ruler bars, its radius and shadow samples, its type specimens, and any sidebar or header divider. Built honestly, those features fail the test. Moving them into inline `style` props would pass it, because the test reads only gallery.css, so the dogfooding rule then has an unpoliced loophole.

**Remedy**

> Decide how these surfaces are styled. Either name a short exception list (for example `gallery-stage` and `gallery-swatch`, which may set background, border-radius and box-shadow from `--bit-*` tokens only), or add the needed primitives to bit. Then say whether the lint also bans or limits JSX `style` props in apps/gallery/src.

### R3-5 — completeness

**Problem**

> The allowlist test 'fails if any `gallery-*` rule sets a property outside a layout-only set'. Rules in gallery.css whose selectors aren't `gallery-*` (for example `body`, `:root`, element selectors, or `.bit-button` overrides) aren't checked at all. A hand-rolled restyle of a bit component through a `.bit-*` override, which is the stand-in the check exists to prevent, would pass.

**Remedy**

> Have the test also fail on any selector in gallery.css that isn't a `gallery-*` class, apart from an explicit short list (for example `html` and `body` with layout-only properties).

### R3-6 — clarity

**Problem**

> `fullFile(jsx)` is said to add 'the component import' itself, but it receives only a JSX string. The gallery calls `fullFile(toJsx(...))`, and the built `toJsx` (apps/gallery/src/code/toJsx.ts) already returns the import line, a blank line and the element. The smoke, meanwhile, calls `fullFile('<Button>Save</Button>')` with no import line. The input contract is therefore contradictory. Either fullFile would have to parse JSX to find component names (including ChildSpec children and parts), or the gallery's output would contain the import line twice, or end up with the import inside the `Example` body.

**Remedy**

> Fix the signature. For example, `fullFile({ importLine, element })` with `toJsx` returning those parts, or `fullFile(toJsxOutput)` that splits off the import line. Make the smoke call it the same way the gallery does, so it tests the gallery's real output.

### R3-7 — feasibility

**Problem**

> Smoke step 3 makes `main.jsx` 'exactly `STYLE_IMPORTS` plus `fullFile(...)`'. fullFile already contains both style imports, so the entry imports them twice. More importantly, the full file only defines an `Example` component and nothing mounts it: there is no `createRoot(...).render(<Example/>)`, and the doc doesn't say whether `Example` is exported. As written, the built page renders nothing, and step 5's Playwright assertion on the button can't pass.

**Remedy**

> Specify the scaffold. For example, write fullFile's output verbatim to `App.jsx` (with `Example` as the default export), and have `main.jsx` import `STYLE_IMPORTS` plus App and mount it with `createRoot`. That also exercises 'skip if already in your entry file'. Record whether `Example` is exported in the copied file.

### R3-8 — feasibility

**Problem**

> `apps/gallery/src/content/snippets.mjs` is plain JS imported by a TypeScript-strict gallery. Without `allowJs` or a declaration file, `tsc` reports implicit-any for the import (TS7016), and the plan's ESLint config ignores `**/*.mjs`, so the shared module would be neither typechecked nor linted. The doc doesn't say how the gallery consumes it under strict TypeScript.

**Remedy**

> Add a `snippets.d.mts` with the three exports' types, or enable `allowJs`/`checkJs` for that file, and decide whether it's linted.

### R3-9 — clarity

**Problem**

> The Success Criteria say the smoke 'proves install → styles (theme first)', and step 4 asserts that the built CSS's first rule is the Google Fonts `@import`. Vite's CSS build hoists `@import` rules to the top of the emitted stylesheet, so that assertion also passes with styles.css imported first. It shows the font import survives, not that the order is right. The README, which T11 edits, isn't tied to `STYLE_IMPORTS` by any check, so it can drift back.

**Remedy**

> Reword the criterion to say that the smoke proves the font import survives a Vite build, and that `STYLE_IMPORTS` is the single source of the order. Optionally add a test that the README's install snippet contains `STYLE_IMPORTS` verbatim.

### R3-11 — consistency

**Problem**

The live docs would then document APIs that `pnpm add @bit-ds/react` doesn't deliver, which breaks premise 3 ('The docs must not promise an install that fails').

**Remedy**

### R3-12 — feasibility

**Problem**

The doc also doesn't say whether the check runs when a re-run skips the publish, and that's exactly the recovery path, where the check should gate the deploy.

**Remedy**
